---
title: Troubleshooting
description: Diagnose known setup, provider, and scheduling failures.
---

## Browser runtime fails to start

If local Agent logs show a Python or Camoufox installation error, check the installed Python version:

- macOS/Linux: `python3 --version`
- Windows: `python --version`

OneGlanse needs Python 3.10+ for the local Camoufox runtime. The setup script can provision it automatically on supported environments.

If auto-detection selects the wrong binary, set `CAMOUFOX_PYTHON_BIN` to the path of a compatible interpreter in `.env`, then restart `pnpm local`.

Provider sign-in needs a visible desktop browser. On WSL, the Agent reports an error when it cannot detect a display. Use WSLg with a working graphical display, or run the sign-in flow from a native desktop OS.

## Redis connection refused

If Web or Agent reports `ECONNREFUSED` for Redis, check that Docker is running and the `redis` container is healthy:

```bash
docker ps
```

For local mode, restart `pnpm local`. That command starts the database and Redis containers before Web and Agent.

## ClickHouse unavailable at startup

If the dashboard or logs report a ClickHouse connection error, check the container and wait for its health check:

```bash
docker logs clickhouse_db --tail 100
```

On a first start, initialization can take time. If the container remains unhealthy, inspect its logs before retrying the app.

## Provider stays disconnected after sign-in

Complete any provider confirmation or two-factor step and wait for the connection status in the OneGlanse Providers page. If it stays disconnected, repeat the local provider sign-in flow. For a VPS, upload the saved session again with `pnpm upload:vps` from the desktop.

## Google sign-in button is missing

Set both `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET` in the Web app's `.env`, then restart Web. These values enable Google sign-in to OneGlanse. They are separate from browser sessions for Gemini and Google AI Overview.

## Prompts remain queued

Check that the Agent worker is running. `pnpm local` starts Web and Agent together; a separate Web development process needs `pnpm dev:agent`. On a VPS, inspect the worker:

```bash
docker logs oneglanse-agent-worker --tail 100
```

Also check provider connection status and Redis health. A provider without a valid session cannot complete its browser run.

## Provider opens but response or citations are missing

Provider interfaces can change independently of OneGlanse. Retry the same prompt once, check the Agent logs for extraction errors, and report a reproducible case in the [issue tracker](https://github.com/oneglanse/oneglanse/issues). Include the provider, approximate time, and sanitized output. Do not include credentials or session files.

## Self-host image pull fails

`pnpm self-host` pulls configured images. If Docker reports `no matching manifest` for the machine's architecture, bootstrap falls back to a local build. Other pull errors, such as registry access or authentication failures, still stop the command. Check Docker's error and outbound registry access, then retry:

```bash
pnpm self-host
```

Use `pnpm self-host:build` when you explicitly need to build the application images from source.

## Migration fails on startup

Check the migration container and Postgres logs:

```bash
docker logs oneglanse-migrate --tail 100
docker logs postgres_db --tail 100
```

Resolve the reported database or migration error, then rerun `pnpm self-host`. The Compose stack runs migrations before Web starts.

## Sessions do not transfer to the VPS

Confirm the Agent is reachable from the desktop and the upload port is allowed by your firewall or private network:

```bash
curl http://YOUR_VPS_IP:3333/health
```

Check that the desktop uses the correct `AGENT_AUTH_UPLOAD_URL` or `ONEGLANSE_VPS_IP`, and that `AGENT_AUTH_UPLOAD_TOKEN` matches the VPS value. A `401 Unauthorized` response means the token was rejected. Check the Agent logs with `docker logs oneglanse-agent-worker --tail 100`.

The IP shortcut uses plain HTTP. Use the secure upload paths in [Self-Hosted Setup](/self-hosted-setup#session-upload-security) before transferring sessions across an untrusted network.

## Recurring schedule is saved but does not run

Recurring schedules require self-host mode. Check that the Schedule page shows a selected cadence and that Web, Postgres, and Agent are running. The scheduler stores a `pg_cron` job in Postgres and calls the Web app through `API_BASE_URL` with `INTERNAL_CRON_SECRET`.

Inspect Web and Postgres logs for `[scheduler]`, `pg_cron`, or scheduled-run errors:

```bash
docker logs oneglanse-web --tail 100
docker logs postgres_db --tail 100
```

Verify that `API_BASE_URL` is reachable from the Postgres container and that startup generated `INTERNAL_CRON_SECRET`. A saved cadence can remain visible even if creation of its `pg_cron` job failed, because that update is best effort. After fixing the cause, save the schedule again to recreate the job. Do the same for schedules saved before an affected version was upgraded.
