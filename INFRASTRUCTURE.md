## Issue I7 — PostgreSQL Extensions Granted to PUBLIC

**Severity:** MEDIUM
**File:** `packages/db/init-scripts/00-init.sql`

```sql
CREATE EXTENSION IF NOT EXISTS "pg_cron";
CREATE EXTENSION IF NOT EXISTS "http";
GRANT USAGE ON SCHEMA cron TO PUBLIC;
```

Two concerns:

1. **`pg_cron`** can execute arbitrary SQL on a schedule. Granting it to `PUBLIC` means any database user can schedule arbitrary SQL execution.
2. **`http`** extension allows PostgreSQL to make outbound HTTP requests. This can be used to exfiltrate data or probe internal network services from inside the database process.

**Fix:**
```sql
-- Grant only to your application role, not PUBLIC
REVOKE USAGE ON SCHEMA cron FROM PUBLIC;
GRANT USAGE ON SCHEMA cron TO onescope_app;  -- your specific DB user

-- Consider whether the http extension is actually needed in production
-- DROP EXTENSION IF EXISTS "http";
```

## Issue I8 — No Resource Limits on Docker Services

**Severity:** LOW
**File:** `docker-compose.yml`

No CPU or memory limits are defined for any service. A single service (e.g., a memory-leaking worker or a runaway ClickHouse query) can consume all available host resources, causing other services to crash.

**Fix — add to resource-intensive services:**
```yaml
deploy:
  resources:
    limits:
      cpus: '2'
      memory: 2G
    reservations:
      cpus: '0.5'
      memory: 512M
```

Services to prioritize for limits:
- `agent-worker` (Playwright + Chromium — high memory)
- `clickhouse` (can be memory-intensive with large datasets)
- `db` (PostgreSQL)

## Issue I9 — TypeScript Version Mismatch

**Severity:** LOW
**Files:** Various `package.json`

| Package | TypeScript Version |
|---------|-------------------|
| Root | `^5.8.2` |
| `apps/web` | `^5.8.2` |
| `apps/agent` | `^5.9.3` |
| All packages | `^5.8.2` |

Mixed TypeScript versions in a monorepo can cause subtle type compatibility issues when declaration files generated by one version are consumed by packages using another.

**Fix:** Standardize to a single version in the root `package.json` and remove all `typescript` deps from individual apps/packages (let them inherit from root via workspace hoisting):
```json
// root package.json
{
  "devDependencies": {
    "typescript": "5.9.3"
  }
}
```

## Issue I10 — `pnpm deploy --legacy` Flag

**Severity:** LOW
**File:** `Dockerfile.agent:21`

```dockerfile
RUN pnpm deploy --legacy --filter @onescope/agent --prod /app/out
```

The `--legacy` flag is a workaround for dependency resolution issues. This can mask underlying problems with peer dependency conflicts that should be resolved properly.

**Action:** Investigate which dependency causes the need for `--legacy` and fix it at source. Run `pnpm install` without `--legacy` to see the full error.

## Issue I11 — No Linting for Agent or Packages

**Severity:** LOW
**Files:** `apps/agent/package.json`, `packages/*/package.json`

The web app uses Biome (`1.9.4`) for linting. The agent app and all packages have no linter configured. This means approximately 60% of the codebase's TypeScript has no automated style or quality checks.

**Fix:** Extend Biome to cover the entire monorepo by adding a root-level `biome.json`:
```json
{
  "$schema": "https://biomejs.dev/schemas/1.9.4/schema.json",
  "organizeImports": { "enabled": true },
  "linter": {
    "enabled": true,
    "rules": { "recommended": true }
  },
  "formatter": {
    "enabled": true,
    "indentStyle": "space",
    "indentWidth": 2
  }
}
```

Then update root `package.json`:
```json
{
  "scripts": {
    "lint": "biome check ."
  }
}
```

## Issue I12 — No Network Isolation Between Services

**Severity:** LOW
**File:** `docker-compose.yml`

All services use Docker's default bridge network, meaning every container can reach every other container. The web app can directly connect to Redis, ClickHouse, and PostgreSQL even if that's not intended.

**Fix — define explicit networks:**
```yaml
networks:
  frontend:
    driver: bridge
  backend:
    driver: bridge
  data:
    driver: bridge

services:
  web:
    networks: [frontend, backend]
  agent-api:
    networks: [backend]
  agent-worker:
    networks: [backend, data]
  db:
    networks: [data]
  redis:
    networks: [data]
  clickhouse:
    networks: [data]
```

## Issue I13 — Migration Script Has Fragile Path Detection

**Severity:** LOW
**File:** `docker-compose.yml` (migrate service command)

```yaml
migrate:
  command: >
    sh -lc '
      if [ -d "/workspace" ]; then
        cd /workspace && pnpm --filter @onescope/db db:migrate
      elif [ -d "/app" ]; then
        cd /app && pnpm --filter @onescope/db db:migrate
      fi
    '
```

The migration script guesses the working directory by checking if `/workspace` or `/app` exists. If neither exists (or a new deploy path is used), migrations silently don't run. No validation confirms that migrations actually succeeded.

**Fix:** Use a deterministic `WORKDIR` in the Dockerfile and remove the path detection:
```dockerfile
# In Dockerfile (migrate stage)
WORKDIR /app
```
```yaml
# In docker-compose.yml
migrate:
  command: pnpm --filter @onescope/db db:migrate
```

## Issue I14 — Build Cache Stale Without Registry-Based Cache

**Severity:** LOW
**File:** `.github/workflows/docker-build.yml:107-108, 144-145, 181-182`

```yaml
cache-from: type=gha,scope=onescope-web
cache-to: type=gha,scope=onescope-web,mode=max
```

GitHub Actions cache has a 10GB limit shared across all workflows. For monorepos with multiple Docker images, the cache evicts frequently. Registry-based cache is more reliable:

```yaml
cache-from: type=registry,ref=ghcr.io/${{ github.repository }}/onescope-web:buildcache
cache-to: type=registry,ref=ghcr.io/${{ github.repository }}/onescope-web:buildcache,mode=max
```

## Issue I15 — No Container Security Scanning in CI

**Severity:** MEDIUM
**File:** `.github/workflows/docker-build.yml`

Built Docker images are pushed without any vulnerability scanning. Known CVEs in base images or dependencies go undetected.

**Fix — add Trivy scanning:**
```yaml
- name: Scan Docker image
  uses: aquasecurity/trivy-action@master
  with:
    image-ref: 'ghcr.io/${{ github.repository }}/onescope-web:latest'
    format: 'table'
    exit-code: '1'       # Fail CI on HIGH/CRITICAL CVEs
    severity: 'HIGH,CRITICAL'
```

## Turborepo Configuration Notes

**File:** `turbo.json`

Minor issues found:

1. **Missing outputs for utility packages:** `packages/types`, `packages/errors`, and `packages/utils` produce `dist/` but this isn't declared in Turborepo outputs. This can cause cache misses.

   **Fix:** Ensure each package's `turbo.json` or root config declares `"outputs": ["dist/**"]`.

2. **No `test` task defined:** Tests cannot run as part of the Turbo pipeline.

   **Fix:**
   ```json
   {
     "tasks": {
       "test": {
         "dependsOn": ["^build"],
         "cache": false
       }
     }
   }
   ```
